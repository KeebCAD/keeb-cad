# Spike verdict: carrying stage outputs from the model worker to the main thread

Question: the architecture moves all derived stages into one model worker. After each applied command the worker posts a stage's whole output to the main thread, with geometry in transferred typed-array buffers, replaced whole in a `shallowRef`. Which way of packing and reading those outputs costs the main thread least, and what does each one cost in the worker and in transit?

The spike's code and evidence live on branch `archive/spike-stage-transport` (commit `07adb0dd5833b7c4b62765ca54214c6fbdc90b5d`), not on main; every `spikes/` and `results/` path below is on that branch. Adopted 2026-11-01: the own struct-of-arrays codec with ids pre-sorted by the worker (spine memlog).

This spike informs an architecture decision. It has no pass or miss sign-off.

> **The verdict run was on battery power** (BAT0 73 %, discharging), with the `power-saver` profile and the `powersave` CPU governor (`results/verdict/run.json`). The machine was not on AC when the run happened. Absolute times are likely higher than on AC. The comparison between candidates holds, because they were interleaved round-robin in the same run. Re-run `pnpm --dir spikes verify` on AC before quoting any absolute number as a budget.

Every number below comes from run `bbfc446a-0fe7-49f1-8fe7-5dd3f65bfa76`, committed in `results/verdict/`:

- `timings-<browser>.json`: median, p95 and max for each metric;
- `samples-<browser>.json`: every sample;
- `correctness-<browser>.json`: the round-trip cases that passed;
- `bundle.json`: bundle sizes;
- `report.md`: all the tables, generated by `node scripts/report.mjs results/verdict`.

## Candidates (versions and licences read from the npm registry on 2026-11-01, pinned exactly)

| # | candidate | version (published) | licence | what crosses the boundary |
|---|---|---|---|---|
| 1 | own codec (`src/own-*.ts`) | n/a | n/a | struct-of-arrays typed arrays, each in its own transferred ArrayBuffer. The main thread reads through accessor views. |
| 1i | own codec + worker-sorted ids (added by the spike) | n/a | n/a | the same as 1, plus a `Uint32Array` of ids in byte order, so a lookup is a binary search with no index to build |
| 2 | FlatBuffers `flatbuffers` | 25.9.23 (2025-09-24) | Apache-2.0 | one buffer, transferred. Readers come from `flatc` 25.9.23 (`schema/stage.fbs` → `src/fb/`). |
| 3 | Apache Arrow `apache-arrow` | 21.2.0 (2026-07-21) | Apache-2.0 | one IPC stream per table, transferred; `tableFromIPC` on main |
| 4 | msgpackr `msgpackr` | 2.1.3 (2026-10-28) | MIT | packed bytes (record extension on), transferred; `unpack` on main |
| 5 | structured clone | n/a | n/a | plain objects, no buffers (the baseline) |
| 5b | own codec → plain | n/a | n/a | the buffers from 1, unpacked into plain objects on main |

**flatc install:** the mise `github:` backend, pinned in `spikes/mise.toml` (`"github:google/flatbuffers" = { version = "25.9.23", bin = "flatc" }`, asset `Linux.flatc.binary.g++-13.zip`). `pnpm gen:fb` runs `mise exec -- flatc --ts -o src/fb schema/stage.fbs`, and `pnpm verify` regenerates the readers on every run. msgpackr's optional native addon `msgpackr-extract` is denied a build (`allowBuilds` in `pnpm-workspace.yaml`) because the browser never loads it.

## Method

- **Workspace.** A standalone pnpm workspace in `spikes/` with its own lockfile and strictness that mirrors the root (`strictPeerDependencies`, `hoist: false`, `publicHoistPattern: []`). It runs Vitest 5.0.5 in browser mode on Playwright 1.64.1, one browser at a time: Chromium 156 (headless), then Firefox 157. COOP and COEP are set and both globals were cross-origin isolated. The timer step was 0.005 ms in Chromium and 0.02 ms in Firefox, in both the page and the worker.
- **Data.** Deterministic fake data from `src/data.ts`:
  - plates, Corney size: a 40-segment outline (every 4th segment an arc) and 50 cutouts of 14 × 14 mm, every 5th with 4 corner arcs, each with an id and a slot id;
  - PCB, Corney size: 50 footprints × 10 pads (id, net, position, shape, size) and 300 tracks;
  - the same at 10×.
  - Ids are random 12-character strings. Nets are about 50 names per board, ×10 at 10×.
- **Worker.** `src/worker.ts` is a real module Web Worker. On each request it packs the output with one candidate (timed), takes `tPost = performance.timeOrigin + performance.now()` just before `postMessage`, posts with the buffers transferred, and then reports how long the `postMessage` call took.
- **Main thread.** `src/harness.ts` and `src/measure.ts` do the main-thread side. The handler's first statement takes `tArrive`. Everything after it is timed inside the same task, including the first read of `e.data`:
  - **first usable:** read `e.data`, build the reader, get the outline's `d` string (plates) or the first pad's position (PCB);
  - **(a) traversal:** every path's SVG `d` string, rounded to 1 µm, or every pad's x and y into a `Float64Array`;
  - **(b) index + lookup:** build whatever id index the candidate needs, then look up one random cutout (slot id and `d`) or pad (position and net). The index build is counted. A separate warm figure gives the mean of 200 lookups after the index exists.
- **Clocks.** Absolute times in both globals are `performance.timeOrigin + performance.now()`. The worker-minus-main offset is estimated NTP-style from 200 empty ping-pongs before and after each output × size block: offset = ((t1 − t0) + (t2 − t3)) / 2. Transit is `tArrive − (tPost − offset)`. The offsets were 0.005 ms in Chromium and 0.010 ms in Firefox, stable before and after each block. That is one timer-step or less, so transit is resolved to about one timer step.
- **Pre-handler probe (mode c).** The probe exists because Firefox deserialises a structured clone before the handler runs, so that main-thread cost would otherwise hide inside "transit". The main thread stays busy in the task that sent the request until the worker has posted, using a SharedArrayBuffer flag, plus 1 ms. When the busy task ends, the time until the handler starts is the main-thread work done before the handler.
- **Runs.** 30 warm-up messages per candidate, then 120 per mode (a, b, c). The 7 candidates are interleaved round-robin. Encode, transit and first-usable figures use n = 240 (modes a and b); the others use n = 120.
- **Repeats.** A repeated figure (×10 over the same payload) checks values that sit near the timer step. It is in `report.md` and not repeated here.
- **Correctness.** `src/roundtrip.test.ts` passes every candidate, output and size through the worker and checks the following, in both browsers (28 cases each):
  - `toPlain()` deep-equals the generated data;
  - every `d` string and every pad position equals the plain reader's;
  - every id's lookup returns the generated values.

## Recommendation

Use the own struct-of-arrays codec with the id order sorted in the worker (1i). The main thread reads typed views straight over the transferred buffers and never builds plain objects or an id index.

1. **Least main-thread cost everywhere measured.**
   - PCB 10×: 0.075 ms in Chromium and 0.04 ms in Firefox from arrival to every pad position read. FlatBuffers and Arrow take 0.4 to 0.6 ms, and structured clone takes 5.4 / 11.5 ms.
   - Lookup by id without an index: 0.02 ms in both browsers at 10×. Plain 1 pays 1.4 to 1.9 ms to decode every id into a Map, and FlatBuffers and Arrow pay 2.8 to 4.4 ms.
2. **Cheapest to pack in the worker after structured clone.** PCB 10× takes 1.5 to 1.9 ms for 1, and 3.7 ms for 1i because of the byte-order sort. FlatBuffers takes 8 to 16 ms, Arrow 8 to 15 ms and msgpackr 3 to 9 ms. In the real worker a stage could write straight into the arrays and skip packing.
3. **Smallest bundle** apart from the baseline: 1.3 KB gzip, with no dependency. Arrow adds 40.9 KB and msgpackr 5.9 KB.
4. **Safe enough.** Correctness is proven by the round-trip test in both browsers.

Two findings matter whichever codec is chosen:

- **Rendering SVG `d` strings dominates the plates read.** At 10× it costs 0.6 to 1.2 ms on every candidate, because number formatting is the work, not the reading. The codec moves plates by tenths of a millisecond. It moves PCB, and lookups, by an order of magnitude.
- **Structured clone of plain objects is the one choice that scales badly on the main thread.** At PCB 10× it blocks the main thread for 5 to 11 ms per message, a large share of a 16.7 ms frame, and in Firefox that time happens before any handler code runs, so no lazy read can avoid it. The architecture's buffer-transfer premise is confirmed.

If a hand-written codec is judged too costly to maintain, the cheapest fallback is 5b: the same buffers, unpacked into plain objects on main, at 0.5 ms for PCB 10×. FlatBuffers is close on traversal but pays a 2 KB larger bundle, 4 to 10 times the worker encode time, and 1.3 to 2.2 times the bytes. Its TypeScript output has no keyed lookup (`lookupByKey` is not generated), so it needs the same index work as 1.

Arrow and msgpackr are not recommended:

- Arrow adds 40 KB gzip and costs 0.2 to 0.6 ms just to open (`tableFromIPC`), even at Corney size.
- msgpackr is an unpack into plain objects, so it costs 1.8 to 3.4 ms on main at PCB 10×. Its record decoding also generates code with `new Function`, which a strict CSP would block. 2.1.3 was published only 4 days before the run.

## What this spike does not show

- **Power state.** The run was on battery (`power-saver`, `powersave` governor) on one machine (Ryzen AI 7 PRO 350), headless, Linux only. Safari/WebKit was not measured.
- **Rendering.** No Vue `shallowRef`, reactivity or rendering cost was measured, and nothing was drawn. "Main total" ends at the data read: `d` strings built, pad positions in a `Float64Array`.
- **Packing.** Every candidate packs from the same ready plain object each time. A real stage that writes its own arrays directly would make encode for 1/1i nearly free. One that builds plain objects first would add that work to every candidate except 5.
- **Allocation and GC.** Each message allocates new buffers, because transferred buffers are detached in the worker. Allocation and GC pressure over a long session, memory peaks, and buffer pooling or SharedArrayBuffer alternatives were not measured. The p95 and max columns include whatever GC happened during the 2 to 3 minute run.
- **Timer resolution.** The step was 0.005 ms in Chromium and 0.02 ms in Firefox. Corney-size values under about two steps (many Firefox cells of 0 to 0.04 ms) are quantised and do not separate candidates. The repeated ×10 figures in `report.md` are the resolved check, taken on warm caches.
- **Lookup scope.**
  - (b) is one lookup per message after a fresh decode. A UI that does many lookups per message would amortise index builds, as the warm-lookup column shows.
  - The plates lookup includes building that cutout's `d` string.
  - The 1i order is by UTF-8 bytes. The ids here are ASCII.
- **Arrow scope.** Arrow was tried as IPC streams only, not by sending raw vector buffers and rebuilding with `makeData`, which might cut its 0.2 to 0.6 ms open cost. Numeric columns were read through `toArray()`, which is zero-copy for one chunk.
- **msgpackr options.** msgpackr ran with `useRecords: true` only. Other options, such as shared structures and `bundleStrings`, were not tried.
- **Bundle sizes.** They include each reader's `toPlain()` (test-only code) and the shared SVG writer, so they are upper bounds. They do not include the worker side.
- **Data.** The data is fake and shaped by the spike: exact arcs, 12-character ids, ~50 nets ×10. Real stage outputs, such as case geometry, other plate layers or 3D meshes, may have other ratios of strings to numbers.

## Reproduce

```sh
pnpm --dir spikes verify     # install (frozen), playwright browsers, flatc codegen, run marker,
                             # typecheck, round-trip + bench in Chromium then Firefox,
                             # build the readers, size them, write results/latest/report.md
cp spikes/results/latest/* spikes/results/verdict/   # only for a run the verdict cites
```

`verify` exits 0 only if every step succeeds and every results file carries the run id from `results/latest/run.json`. The bench test has a 20-minute timeout and the round-trip test a 5-minute one. Each browser takes about 2 to 3 minutes for the bench.
