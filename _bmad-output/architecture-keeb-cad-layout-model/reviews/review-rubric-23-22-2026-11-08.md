## Medium

### M1. "Imported only by" has no fence

> `# editor/devtools: dev-only inspectables module, imported only by app's main start file` (Seed)

This is a Rule stated only in a Seed comment. AD-25's **Entry fences** sentence is unchanged and does not list it, and `.dependency-cruiser.mts` has no rule for it. `GRAPH.app` allows `editor` and `ws('editor')` matches any subpath, so any `app/src/` file, or any `editor` file, may import the subpath.

The build check doesn't cover this. It catches a leak into production, but a second importer behind its own `MODE` gate ships nothing and passes. A second `addModule` would then double every inspector entry silently, because multi tokens accept repeat registrations (`container.spec.ts`, "does not throw DuplicateRegistrationError when registering the same multi-token twice"). The harm is dev-only, which keeps this at medium. The stated rule still prevents nothing as written, and every sibling "only X imports Y entry" in AD-25 is a real check.

Fix: add a clause to AD-25's Entry fences, for example "only `app`'s main start file imports `editor/devtools`". The ticket then adds one `onlyOwnersImportEntry('editor', 'devtools', ['^app/src/(main|start-main)\.ts$'], …)` row, the shape `model/worker` already uses (its owner regex also names the start file), and its fixture in `tooling/ad10/violations/`. That helper already includes `editor`'s own files in `from`, so it also stops an `editor` file importing the entry.

### M2. The new decision has no rejected alternative

> `` `editor` has one development-only subpath, `editor/devtools`, which exports only the module that fills `inspectables`; `app`'s main start file adds it through a dynamic import behind `import.meta.env.MODE === 'development'`, before `autoLoad()`. ``

AGENTS.md: "Give every decision its rejected alternative: 'X, not Y, because Z'. This covers … a spine sentence that chooses between options." This sentence chooses, and the ticket's `unknown` shows options existed. No Y is given. Two choices are unrecorded:

1. **Registering from `app`, through a subpath.** The obvious Y is the one the ticket rules out: `mountEditor` registering the module itself. It cannot, since `Injector` has only `resolve` (`packages/di/src/types.ts`), and that is a ready-made Z.
2. **Exporting only the module, keeping the plugin behind `mountEditor`.** This departs from the ticket's pick ("editor exports the plugin and the module from a dev subpath"). It is what creates a second gate and second chunk.

📐 The amendment does not weigh a one-gate shape: `app`'s start file imports both plugin and module from the subpath under one `MODE` gate and hands the plugin's setup to `mountEditor` as an optional argument. That leaves `editor` with no gate, a single condition, a single toggled bug, and makes "imported only by" cover both pieces. Its cost is reopening the 23.20 sentence "`mountEditor` loads it through a dynamic import" and widening `mountEditor`'s signature. The two-gate shape may well be right, but this is the Y it should name and beat.

### M3. The ticket's proof covers one gate; the spine now has two

> `a build check proves neither gate ships it: app/dist holds no trace of the plugin's id, which every inspectable's id carries.`

The check itself works for both gates: without `mountEditor`'s gate the plugin chunk ships the id, and without `app`'s gate the module chunk ships it through the inspectable ids. But 23.22's `verify` says "does once the MODE gate is removed (a toggled bug)", singular. A plan that follows it toggles one gate and the other stays unproven. Its `unknown` also still says the plugin is exported from the subpath, which the spine now rejects, and its description says "behind the same gate" without naming `app`'s start file.

Fix (ticket, alongside this spine commit): `verify` toggles each gate separately, the `unknown` is cleared to the spine's decision, the description names the start file.

## Low

**L1. One gate or two.** ☝️ The glossary says "the devtools `MODE` gate" and the row says "the same `MODE` gate", then "neither gate", so the count shifts from one to two. "Proves neither gate ships it" also reads oddly: "it" is the plugin, which `app`'s gate does not guard, and a gate doesn't ship anything. Suggest: "two gates on the same `MODE` condition" once, and "a build check proves both gates hold".

**L2. Two names for one place, in one bullet.** AD-25 now says "`app`'s main start file adds it" and, a few sentences later, "`main.ts` adds `commands`' modules". The code does the second in `start-main.ts` through `main-modules.ts`, and `main.ts` only re-exports. The second sentence is old, but the amendment makes the mismatch visible. Suggest "the main start file" in both.

**L3. Gate evidence is for a different expression.** The Stack note verifies "no chunk for a dynamic import under `import.meta.env.DEV`", while the spine's gates use `MODE === 'development'`, now at two sites. The build check with its toggles settles this, so no spine change is needed beyond M3.

**L4. The id rules name no check.** > "Every inspectable's id starts with the plugin's id"

Nothing named enforces it, and one unprefixed entry doesn't defeat the build check as long as another carries the id. It is cheap to test in `editor` over the module's entries, so the plan should say so. The proof also needs a plugin id that occurs nowhere else in `app/dist`: a generic id such as `keeb-cad` would fail the check. Leave that to the plan, but it should be stated there.

- **AD-10 / graph:** `app → editor` is drawn and `ENTRY_ONLY` has no `app → editor` entry, so no edge or table change is needed for the import. `package.json`'s `exports` holds only `.` today, so `./devtools` is new and `exportsFields` will resolve it.
- **Worker fence:** `worker-entries-reach-no-ui` uses `ws('ui|editor')`, which matches the subpath.
- **Main fence:** the module reaches no `pipeline`, stage or sandbox package as described.
- **Tokens:** `inspectables` is a multi token, and AD-25's table covers `createToken` objects only, so no table row is needed.
- **Gates drifting apart:** the plugin without the module resolves `[]` (`container.ts`, multi with no bindings), giving an empty inspector rather than a crash. No rule needed.
- **Seed vs AD-10:** "imported only by app" stays true, and the new comment narrows it without contradiction.
- **Editor state row vs AD-25:** the two new passages say the same thing, and the row points to AD-25.
