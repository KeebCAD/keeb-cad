# Reality review: DesignPatcher and DesignStore amendment (2026-11-03)

Scope: the spine diff (design store, `DesignPatcher`) checked against installed immer 11.2.9 (source in `node_modules/.pnpm/immer@11.2.9/node_modules/immer/src`, d.ts in `dist/immer.d.ts`) and `packages/di/src`. Empirical scripts: `/tmp/claude-1000/-home-ruyu-projects-keeb-cad/523fc8db-d022-4aca-aff7-552839ea7e54/scratchpad/t.mjs` and `t2.mjs`.

Verdict: the freeze claims and the di claims hold; one claim is worded wrongly (enablePatches) and one path (the mirror's whole-value load) is asserted frozen but not covered by the mechanism named.

## Checked and true

- Version: lockfile and install are immer 11.2.9; `packages/design/package.json` declares `^11.2.9`, matching the spine's tech table.
- `produceWithPatches` deep-freezes its result. `processResult` calls `maybeFreeze(scope, result, true)` when `immer_.autoFreeze_` is on; `freeze(obj, true)` recurses via `each`. Empirical: result deep-frozen with an unfrozen base, an unfrozen base with untouched subtrees, and a freshly inserted unfrozen subtree (the inserted object itself becomes frozen, so a caller's input object is frozen in place, which is why the spine's "inputs are a fresh parsed copy" rule matters).
- `Immer#applyPatches` on the instance runs `this.produce(...)`, so it uses the instance's autoFreeze and deep-freezes. Empirical: applyPatches on a frozen mirror base with an unfrozen patch value gives a deep-frozen result. A root `replace` patch value is adopted by reference and frozen in place.
- Patch `value`s are the same references as in the produced result, and frozen. Fine for structured clone to the worker.
- `new Immer({ autoFreeze: true })` is the library default; stating it is harmless and explicit.
- di: `useClass(ctor)` is called per container; `Bindings` is per `Container`, so the same class registered in main and worker containers is independent (separate instances, separate realms anyway). A class is its own token (`isToken` accepts class constructors). `.eager()` exists on `RegistrationOptions`, and `autoLoad()` resolves eager entries in registration order, which the spine also relies on ("each awaits autoLoad() before it listens").

## Findings

1. Wrong claim: "calls `enablePatches()`, never the global default" (spine Writing bullet). In 11.2.9 `enablePatches()` is a module-global function (`src/plugins/patches.ts:35`, `loadPlugin` writes a module-level `plugins` map, first call wins). There is no per-instance patches switch, and the instance cannot be isolated from it. Empirical: after one `enablePatches()`, a second `new Immer({autoFreeze:false})` also produces patches; before it, `produceWithPatches` throws "plugin for 'Patches' has not been loaded". Consequences: (a) "not the global default" is only true of the `Immer` instance (vs the exported `produce`); the plugin is global per JS realm, so rewrite to say that; (b) calling it from the `DesignPatcher` constructor works and is idempotent (second call is a no-op for the plugin; I ran it twice with no error), but in dev it pushes the extra error strings onto the global `errors` array again each time, so prefer calling it once at module load of `DesignPatcher`'s file, not per container construction (tests build many containers); (c) any other `Immer` in the same realm gets patches too, which only matters if the `immer` fence ever breaks.

2. Gap: the mirror is "deep-frozen" only if its initial whole-value load is frozen, and the spine names only `DesignPatcher.apply` as the mirror's freezer. `workers` sends the whole design value at worker start, on restart and on `replaceDesign` (spine mirror paragraph); that arrives by structured clone, unfrozen. `apply` never touches it. Empirical: `applyPatches(base, [])` and a no-op `produce` on an unfrozen base return the base as is, and when the base is shallow-frozen with unfrozen children (`Object.freeze({a:{b:{c:1}}})`) the nested objects stay unfrozen (`freeze()` returns early on `isFrozen(obj)`). So the first patch after load would produce a frozen root while untouched subtrees from the unfrozen load stay mutable only if they were not copied; in practice the modified path is copied and frozen, but the untouched siblings are frozen too (deep freeze reaches them, test 3), so the real hazard is narrower: between load and the first patch, and for any no-op or empty-patch apply, the mirror is mutable and Vue could proxy it. Fix: say that `design/worker` deep-freezes the whole value on load (Immer's `freeze(value, true)`, as `replaceDesign` does on main), or give `DesignPatcher` a `freeze` method used by both.

3. Edge worth stating: `change` with a recipe that returns a `Rejection`. The spine says the rejection is kept outside the producer (recipe returns `undefined`). Confirmed necessary: if the recipe returns a non-undefined object without modifying the draft, Immer treats it as a replacement of the whole state and emits `[{op:'replace', path:[], value:<the object>}]` (t2.mjs); returning one after modifying throws (error 4). So the "keep it outside" wording is correct and load-bearing; a test should assert it.

4. Minor: a shallow-frozen but not deep-frozen base is a real-input shape only if something other than `replaceDesign` hands `change` a value. With the spine's two writers (commands, `replaceDesign` which deep-freezes) it cannot arise on main. No spine change needed beyond finding 2.

5. di: nothing in the kernel prevents registering `DesignPatcher` in both containers, but nothing prevents adding both modules to one container either, and a second registration of a single token throws `DuplicateRegistrationError` (`bindings.ts`). Where a test or the app composes main and worker modules into one container (e.g. a pipeline-in-main test), the two `design` modules collide. The spine's "main entry never reaches `design/worker`" covers production; add a note that tests of `pipeline` on the main thread use the worker module alone, or have `design/worker` skip registering if `DesignPatcher` is already present (not possible without `override`; simplest is the note).

6. `.eager()` is not mentioned for `DesignStore` or `DesignPatcher` in the diff or the spine (grep: `eager` appears only in the di description and the `autoLoad` lines). If the store must exist before the first command (for the duplicate-command-id check "at startup"), it needs `.eager()` or an explicit resolve in the app entry; a lazy store would only fail on first use. The kernel supports it (`RegistrationOptions.eager()`, `autoLoad()`), so this is a wording gap in the spine, not a kernel gap.
