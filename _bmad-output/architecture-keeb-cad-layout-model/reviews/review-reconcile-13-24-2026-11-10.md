# Reconcile 13.24 (and 13.7's selection) against the amended spine, 2026-11-10

Scope: tickets.toml entries 24 (13.24), 7 (13.7), 23 (13.23, only where it shares keys); epic Notes of 2026-11-10; spine diff (UiAction, invoke path and input builder glossary rows; Editor state row; AD-26 Shortcuts bullet) and the last 13 .memlog.md entries. Nothing was fixed.

Verdict: the spine answers 13.24's one named unknown (where the UI-state availability check lives), but 13.24's text still describes the pre-amendment model in four places and leaves the add flow, G/S gating, root selection and focus unspecified.

## 1. Not answered, or answered differently

1. **Unknown is settled; ticket still blocks on it.** Spine: selection operations are UiActions (`DeleteSelection`, `DuplicateSelection`) whose `available()` reads workspace, focus and selection, then asks `invoke.available(command, input)`. 13.24 still carries `unknown` and "13.24 is not ready until then" (the epic Note "Open question (2026-11-10)" likewise). Product owner to clear both.
2. **Canvas focus, silently added by the spine, absent from 13.24.** Spine: on the Layout workspace Delete needs canvas focus (Landmarks exposes the focused place) and is unavailable elsewhere, including the tree slide-out, "until a story gives Delete a meaning there". 13.24's verify says "Delete removes the selection from the canvas and the tree" and never says the canvas must have focus; a verify step that deletes with focus in the tree would now find Delete unavailable. EXPERIENCE.md line 255 ("Delete what has keyboard focus (layer tab, row, or canvas selection)") makes a tree-row Delete arguably expected; the spine defers it. Needs a PO decision and a verify row (Delete unavailable with focus off the canvas). Whether Ctrl+D also needs canvas focus is not stated by the spine ("each UiAction decides"); 13.24 says nothing.
3. **G and S are not covered.** Spine only designs selection operations (Delete, Duplicate, nudge, rotate, P). G/S are not selection operations and need an add flow with an id field. Open: which handle owns the G/S hotkey (a UiAction that opens the flow, then `invoke(AddGroup, {id,...})` with the flow's explicit input, is the pattern the spine allows but does not state), whether G/S need canvas focus, and where the new node goes (spine: omitted parent = root; 13.24 does not say whether it goes under the selected group). The add flow, minted-id prefill (spine: UI prefills minted id, user may edit) is consistent, but the flow's own state and where it lives (editor UI state?) is unspecified.
4. **"An id already in the design is refused" is only half answered.** Spine: model refuses with `id-taken` (and a malformed id fails `idSchema` as `input-invalid`). Not stated: whether the flow pre-checks (and greys the confirm) or shows the rejection from `invoke`'s result, and whether the flow stays open with the typed text. Because `apply` returns the command's result (AsyncResult), the flow can read it, but the UX is the PO's.
5. **Root selected.** Spine: `DeleteNode` and `DuplicateNode` both refuse the root with `root-required`; the model check runs inside `available(design, input)`, so Delete and Ctrl+D are unavailable (greyed) with the root selected, not refused. 13.24 covers only "nothing selected". Verify has no root row; whether the root can be selected on canvas/tree (13.7) is also unstated.
6. **Delete with an empty selection.** Spine decision: unavailable, not `input-invalid`. 13.24 says it only for Ctrl+D; add Delete to the verify.
7. **Duplicate of a multi-selection.** Spine is silent on arity; it says `DuplicateSelection.available()` asks `available(DuplicateNode, {id})` with the exact input apply will pass. How a multi-selection yields "no input" (builder returns nothing vs `DuplicateSelection` checks `ids.length === 1` itself) is not stated; 13.24's "exactly one" rule is consistent, but the check is now the UiAction's, and the unit tests should say so.
8. **Stale selection after Delete/undo.** Spine: selection drops ids the design no longer holds on each commit event. 13.24 verify ("Delete removes the selection from the canvas and the tree") is consistent, but the ticket does not say the selection is empty afterwards, nor what happens on undo (undo restores nodes; selection is not restored; the spine is silent on that).
9. **Two reports per keypress.** Spine: one key press reports twice (UiAction, then the command). 13.24 has no row on how the user sees a command refusal reaching the caller (toast? status?), nor on the undo stack (one entry, not two; spine says the UiAction is never undoable itself). A verify row ("Ctrl+Z after Delete restores it in one step") is missing.
10. **Palette/menus.** Spine adds the palette-focus rule (palette asks against the pre-open region); 13.24 builds no palette so nothing to change, but no one consumes `available` yet (memlog flow trace: no UI consumer), so 13.24 is the first consumer: it must say where "unavailable" shows (hotkey does nothing? greyed hint on the canvas hints?). Current verify only says "is unavailable and the design unchanged".
11. **Ctrl+D collides with the browser bookmark chord.** The spine's chord rules list reserved chords (W, T, N, Q, L, Shift variants) and require `preventDefault` on every Ctrl chord; D is not on the list, so it is allowed. The ticket should still verify `preventDefault` (no bookmark dialog), and Firefox/Chromium both bind it. 📐
12. **13.7's selection is under-specified against the new lean-selection rule.** 13.7 says "click selects, and 23.8's tree ... stays synced" but not: the selection service holds node ids only (`Id[]`, selection order), session-only; drops stale ids on commit; where it lives (`editor`, a `di` service); that 13.24 reads it through that service. Nothing contradicts, but 13.24 depends on 13.7 building it to the spine's shape; the spine's rule that a node's kind/parent/side are read from the design must hold for 13.7's canvas (click on a part rectangle of a slot selects the slot id, not a part id). Selecting several (Shift-click) is not in 13.7, consistent with the deferral.
13. **Hotkey wording.** 13.24: "its hotkeys join the canvas keys 13.23 adds (F)". Spine: hotkeys are static `hotkeys` on handles; F in 13.23 needs the same treatment (a UiAction too, since it reads selection), and the shortcut registry refuses duplicate ids but not duplicate hotkeys (left to review). Unaddressed: who reviews the G/S/F/Ctrl+D/Delete set for a shared hotkey.

## 2. Lines that now contradict the spine (rewrite by the product owner)

Quoted ticket text -> spine text it conflicts with.

A. 13.24 description: `and the UI answers it unavailable unless exactly one node is selected, an availability check over UI state, not the command's check over the design (Sergii 2026-11-10; where that check lives is this entry's unknown; ...`
Spine (AD-26 Shortcuts): `its available() reads the workspace, the focused region and the selection, then asks available(command, input) with the exact input its apply will pass` and the command's `available(design, input)` now does check the design (root-required, unknown-target). So "not the command's check over the design" is wrong: both layers check; the UiAction owns the UI-state part, the command the design part. "is this entry's unknown" is settled.

B. 13.24 description: `each runs through the design store`
Spine: `Every invocation from the UI ... goes through one editor invoke path`; `a routing UiAction's apply runs its command through the invoke path` (memlog 'routed run'; rejected 'the router calling the design store directly'); and Editor state: `a composable runs an entry only through the invoke path`. Should read "through the invoke path".

C. 13.24 unknown field: `the invoke path answers available(handle) only from a UiAction's, an action's or a command's own check, and a command sees only the design (packages/editor/src/invoke/invoke.ts:61-69; spine AD-26 Shortcuts). Candidates: an optional check on the per-entry input builder, a UiAction that checks the selection and runs DuplicateNode, a check in the invoke path.`
Spine: `available(handle, input?)` takes input; a command's check is `available(design, input)`; input builder rejected (A), selection arity on the command rejected (C); UiAction chosen. Whole field is obsolete. Also 'invoke order' changed (input built and parsed first, then availability) which invalidates the cited line numbers (invoke.ts:89-90, design-store.ts:155-159 are replaced by the code 13.24 must change).

D. 13.24 description: `Ctrl+D duplicates the one selected node ... (DuplicateNode takes one id)` and `Delete deletes the selection (one DeleteNode with the selected ids)` plus `each runs through the design store, on story 7's selection`
Spine: Ctrl+D and Delete are hotkeys of the UiActions `DuplicateSelection` and `DeleteSelection`, not of `DuplicateNode`/`DeleteNode`: `the commands themselves carry no hotkey for these operations`. The ticket names the commands as the things bound; it must name the two UiActions (class files, per AGENTS.md naming) as 13.24's code, plus the changes it forces in `editor`: `UiAction.apply` returning `AsyncResult<void, Rejection>`, `Invoke.available(handle, input?)`, parse-before-availability order in `Invoke` and `DesignStore`, `Command.available(design, input)` with the shared model check, Landmarks' focused-place read, the selection stale-drop. The description lists none of these; they are 13.24's scope (nobody else owns them) and the plan cap needs checking.

E. 13.24 verify: `with nothing selected Ctrl+D is unavailable and the design unchanged; Delete removes the selection from the canvas and the tree.`
Spine: `Delete ... needs canvas focus and a selection`; elsewhere unavailable. The verify must state focus on the canvas (or it is ambiguous with the tree), and add rows: Delete with nothing selected unavailable; root selected unavailable for both keys; two nodes selected makes Ctrl+D unavailable; focus in the tree makes Delete do nothing; a refused routed command reaches the caller (not reported as success); one Ctrl+Z restores the delete.

Spine and memlog now settle it. Close the line in the epic (and in deferred-work.md if the same unknown is listed there).

Not contradicted, but its mechanism ("by an availability check over UI state") should now say the UiAction `DuplicateSelection`. deferred-work.md line 439 says `the invoke path answers it unavailable otherwise`: now the UiAction's check, via the invoke path.
