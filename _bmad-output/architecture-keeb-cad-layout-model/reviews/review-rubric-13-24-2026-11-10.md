# Rubric review: spine amendment 13.24 (2026-11-10)

Scope: glossary rows UiAction, invoke path, input builder; AD-2 `Commands and actions` bullet; AD-26 `Shortcuts` bullet; Editor state row. Checked against the last 13 `.memlog.md` entries and the code in `packages/editor/src/invoke/`, `ui-actions/`, `landmarks/`, `packages/design/src/store/design-store.ts`, `packages/commands/src/layout/`, `packages/model/src/layout-editing/delete-node.ts`.

Verdict: the amendment lands almost every memlog decision, but it leaves `root-required` and `unknown-target` reachable only through a path the new availability check now blocks, contradicts itself on `available` with no design open, and states several code behaviour changes as if they were already true.

Spine line numbers refer to the working-tree file (glossary 127-129, AD-2 bullet 215, AD-26 bullet 703, Editor state 1079).

## Findings

### 1. HIGH: the availability check swallows `root-required` / `unknown-target`

Spine (215, 703, 1079; 228 unchanged):
- `a refusal decidable by reading the design and the input, such as DeleteNode's `root-required` and `unknown-target`, lives in one `model` check function that both call, so availability and apply can't disagree`
- `so `unknown-target` stays a stale or malformed request`
- 228 (unchanged): `` `DeleteNode` takes a list of ids, refuses the root with `root-required` and any id the design lacks with `unknown-target` ``
- 215 (unchanged): `it parses the input and checks availability before the apply step, for both kinds`

Code: `packages/commands/src/layout/delete-node.ts` has `available(_design): boolean`; `packages/design/src/store/design-store.ts:156` returns `{ kind: 'unavailable' }` when `#commandAvailable` is false, before `apply`.

Problem: `available` returns a boolean and the store maps false to `unavailable` before apply. Once the check carries `root-required` and `unknown-target`, `run`, `runById` (reference-design scripts, posted violation fixes) and `invoke` return `unavailable` for those inputs, never `root-required` / `unknown-target`. Line 228 and the `ModelRejectionKind` entries (773) become unreachable through the store, and `unknown-target stays a stale or malformed request` is false: a stale request now reads `unavailable`. The behaviour change (rejection kind returned for a bad Delete) is nowhere stated. "Availability and apply can't disagree" is also unenforceable as written: nothing says what the shared function returns or how the store reports it.

Fix: decide and state one of: (a) the check returns `Option<Rejection>` and the store returns that rejection as-is, `unavailable` being only for "no design open" and for checks with no rejection kind (then `available()` = "check returns none"); or (b) `unavailable` replaces both kinds and 228/773 are amended. Say which in AD-2, and name the change to `run`'s result. Option (a) keeps data-driven callers (`runById`) seeing the specific kind.

### 2. HIGH: `available` contradicts itself with no design open

Spine (129, 703): `A parse failure answers `true` from `available` and `input-invalid` from `invoke`` and, in the same sentence block, `a command being unavailable while no design is open`. The order stated is `it builds the input ... and parses it, then asks`.

Problem: with no design open and a malformed built input, `available` answers `true` (parse first) while the no-design rule says unavailable. `invoke` answers `input-invalid`, where `packages/editor/src/invoke/invoke.ts:88-90` comment says asking first "keeps the store's no-design throw out of reach" (store `#committed()` throws before parse, `design-store.ts:144`). The new order puts the builder and parse ahead of the no-design guard.

Fix: put the no-design (and, for actions, `Option<Committed>`) check first in the stated order, or state that parse failure wins and that `#committed()` must not throw before parse.

### 3. MEDIUM: code changes presented as present fact, not as changes

The memlog says "Replaces today's order" and records that nothing consumes `available` yet. The spine states the end state without marking what moves in `ratified` code:
- `packages/editor/src/ui-actions/types.ts`: `apply(input: Input): void`; spine: `apply(input)` returning `AsyncResult<void, Rejection>`. `invoke.ts` `#invokeUiAction` discards apply's value and returns `AsyncResult.ok()`.
- `invoke.ts:89`: `available(handle: EntryHandle): boolean`, no `input` parameter; spine: `available(handle, input?)`.
- `invoke.ts` checks availability before building input and before parse (`#invokeCommand`); spine: build, parse, then availability. The store does the same (`design-store.ts:155-159`).
- `Command.available(design)` in all 7 layout commands; spine: `available(design, input)`.
- `Landmarks`: `#focusedPlace()` is private (`landmarks.ts:55`); spine: `Which region holds focus is read from `Landmarks`, which already owns the regions for F6`. The memlog decision is "Landmarks exposes the focused place ... as a read"; the spine never says a read is added or what it returns.
- Memlog: "elsewhere it is unavailable until a story gives Delete a meaning there (layer tab, row)". The spine only says `each UiAction decides whether focus matters`; the Layout-only-for-now rule did not land.

Fix: one sentence in AD-26 listing what the code does today versus the rule ("today `apply` returns void and `Invoke` checks availability first; the build story changes both"), a named public read on `Landmarks` (e.g. the focused place or none), and the Layout-only-for-now sentence.

### 4. MEDIUM: stale hotkey-ownership sentences now contradict the UiAction rule

- 703 (unchanged, same bullet as the new text): `The entries' hotkeys are entry data, declared with each handle in `commands`.`
- 215 (unchanged): `A handle's optional static `hotkeys` is read only by `editor` (AD-26).`
- New 703: `A selection operation (Delete, ...) is a UiAction, not a command with a hotkey`; UiAction row: statics include `hotkeys` declared in `editor`.

Fix: change the first to "declared with each handle: in `commands` for commands and actions, in `editor` for UiActions". The 215 sentence is fine if UiAction is excluded; say so.

### 5. MEDIUM: key rules are stated but not enforceable, so the divergence they target can reopen

- `with the exact input its `apply` will pass`: `UiAction.available()` is nullary (`ui-actions/types.ts`) and the input builder / parse step the invoke path runs for a UiAction is unrelated to the command input `DeleteSelection` assembles from the selection. Nothing makes the two assemblies agree, and nothing is checked. The spine also says `asks a UiAction's own check` after parsing the UiAction's input, but that check receives no input.
- `is a UiAction, not a command with a hotkey`: no rule stops a story giving `DeleteNode` its own `hotkeys` or a menu item bound straight to `DeleteNode` plus an input builder, producing a second Delete path with the missing-selection behaviour the memlog decision 1 forbids. Decision 1 (`an entry that needs a selection it doesn't have is unavailable ... not run and refused with input-invalid`) is never written as a rule; it exists only implicitly via the UiAction pattern. The spine does not say that the shortcut registry refuses a command or action `hotkeys` for selection operations, or that it is a reviewer rule.
- Unavailable hotkey press: the spine does not say what happens (silent no-op, or `unavailable` reaches the timeline and a toast). With Delete bound globally and `unavailable` whenever focus is off-canvas, this is the common path.

Fix: require one private method on the UiAction that builds the routed input, called by both `available()` and `apply`, and a spec row per selection operation proving both agree; state decision 1 as a rule ("a selection-dependent entry with no selection is unavailable; its input builder is never the place to refuse"); state that selection operations are reached only through their UiAction (reviewer rule, since lint cannot see it, like the existing composable rule); state the hotkey-with-no-effect behaviour.

### 6. MEDIUM: decisions in the spine lack the rejected alternative AGENTS.md requires

AGENTS.md: `Give every decision its rejected alternative: "X, not Y, because Z". ... a spine sentence that chooses between options`. The memlog carries the rejected options (builder-owned availability, arity on the command, store dry run, parse failure answering `unavailable`, `{ id, kind }` selection entries, a separate glossary term); the spine text has none. Affected: UiAction-not-command routing, `available` answering `true` on parse failure, pre-check by `available(command, input)` not a store dry run, ids-only selection, Landmarks read not per-region hotkey scoping.

Fix: add a short "not Y, because Z" clause to each, from the memlog.

### 7. LOW: smaller gaps

- UiAction row: `apply(input)` returning `AsyncResult<void, Rejection>` covers a routed command only. A selection UiAction that routes to an action (async, `ActionError`) has no typed home. Say routing targets commands only, or widen the error type.
- Glossary UiAction: `never in the design store and never undoable itself` reads two ways ("the UiAction is never registered in the store" vs "never writes to it"); the row also now writes through `invoke`. Reword to "is not an entry of the design store".
- Shortcut registry row (128) is unchanged and still correct; no edit needed.
- Editor state: the selection service has no name or owning concept folder, and the order of the commit-event subscriber relative to other subscribers (autosave, pipeline post) is unstated; harmless for ids-only pruning but 13.7 will have to choose.
- The memlog's "one key press reports twice ... devtools timeline" landed ("reports twice") but the timeline consequence is not in the Editor state timeline sentence (1079), which still describes "an event `Invoke` emits per call"; with routing, nested calls emit two events and the order (inner first, from `#reported` ordering) is undefined in the spine.
