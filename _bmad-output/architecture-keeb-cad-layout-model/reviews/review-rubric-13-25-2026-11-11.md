## Findings

F1 (medium). The routed-input rule undercuts its own rationale.
Quote: "A parse failure of input the caller passed, whoever built it (a form's typed text, a selection UiAction's routed input), is an `input-invalid` refusal from both ... not ok, because the person's text is then refused with no reason until they confirm."
`DeleteSelection.available()` / `DuplicateSelection.available()` (in `packages/editor/src/selection/`) build `{ ids }` from the selection and pass it to `invoke.available(DeleteNode, input)`. That is code-built input, not a person's text. If it ever fails a refinement, `available` now refuses, the key is not claimed, and the entry greys. That is the "bug would then hide" outcome the previous sentence rejects for builders. The memlog accepts this (compiler mostly covers it; rejected "second path"). Suggested wording: say the residual risk once, e.g. "a refinement the compiler can't see in a UiAction's routed input greys the entry; accepted, not a second path, because the compiler covers the rest". Right now the two sentences read as inconsistent.

F2 (medium). Silent on the UiAction's own `available()` type, which is where the new `Result` is dropped.
Quote (line 127): "`available()` over UI state"; (line 705) "then asks a UiAction's own check ... (ok means available)".
The selection UiActions return `boolean` from `available()` and flatten the nested `Result` with `.getOr(false)`, so a nested `input-invalid` reason is lost and `Invoke.#checkUiAction` reports plain `unavailable`. That is fine for keys, but the rule never says that the UiAction's check stays boolean and that the reason is not forwarded. 13.25 builders will decide this by accident. Add: "a UiAction's `available()` stays a boolean; the path reports `unavailable` for it".

F3 (low). Skipped check on built-input parse failure is implicit.
Quote: "A parse failure of input the path built ... answers ok from `available`".
Today `store.available` is called with the unparsed input and returns `input-invalid`, so nothing checks the entry's availability. "Ok" therefore also means an otherwise-unavailable entry shows enabled for that malformed case. Acceptable, but say it ("without asking the entry's check"), so a test row for it is not a guess.

F4 (low). Precedence of parse vs unavailable for caller input is not stated.
Quote: "in the same order as `invoke`: ... then builds the input ... and parses it, then asks a UiAction's own check ...".
The order implies a bad typed input beats `unavailable` of the entry, and the no-design check beats both. That matches `#checkUiAction` (parse first). It is only inferable; one clause in the add-flow story would pin it. Also note the compile-time claim ("only what it can't see (a pattern or length refinement) reaches that refusal") is true only for typed callers; an untyped `unknown` from a form field reaches it for every wrong type. Qualify to "a form's string field".
