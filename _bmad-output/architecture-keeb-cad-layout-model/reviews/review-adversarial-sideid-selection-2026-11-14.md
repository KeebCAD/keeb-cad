# Adversarial review: side-qualified selection and hover (amendment of 2026-11-14)

Scope: the three spine edits (Editor state row, glossary `add flow`, AD-26 selection operations), checked against the rest of the spine, EXPERIENCE.md (Both halves, Direct edits, Open Items) and ticket 13.8. Spine untouched.

Verdict: the model (SideId in the selection, nodeIdOf to read the node) is sound and the rejected alternatives hold, but it is not yet closed. It leaves the unibody form broken, scopes the select-only rule to two commands when EXPERIENCE says "any workspace", and names no owner for composing/qualifying ids. Fix findings 1 to 3 before 13.8 and 13.24/13.25/13.32 build in parallel.

## F1 (High): the Tree and add flow hard-code `left/<id>`, which does not exist in unibody
Spine: "The Tree, which has no side, selects and points at `left/<id>`" and "the flow's `finished` selects the new node on the side the person was on (`right/<id>` from a right-side selection, else `left/<id>`; 13.8)".
Conflicts: glossary `side` ("`left` and `right` in split forms, `whole` in unibody"), the authored-layout rule ("`left` in split forms, `whole` in unibody ... side-qualified ids, for every form"), the memlog ("unibody `whole/<id>` alike") and `type SideId = Brand<`${'left' | 'right'}/...`>` (l.985).
Incompatible builds: unit A (Tree) selects `left/x`; the canvas items are keyed by posted ids `whole/x`, so nothing highlights, F fits nothing, the dim-until-selected rule never lifts. Unit B (canvas) selects `whole/x`, which is not a `SideId`, so either the brand is widened in `schema` (a Data Schema change nobody owns) or it is cast. Commit pruning keys on node existence only, so the dead `left/x` survives and the stale-id guarantee ("a selection names only existing nodes") is satisfied while selecting nothing drawn. M1 is split-only, but the spine states the model is ready for unibody and the test builders cover `aUnibodyForm`.
Fix: say "selects the authored side's id: `left/<id>` in split, `whole/<id>` in unibody (the side `model` posts for the authored layout)", name one helper (finding 3) that returns it, and decide the type: either selection holds `PlacementId = SideId | whole/...` (new name in `schema`, Data Schema entry first per AGENTS.md policy), or widen `SideId` to `left|right|whole` and say overrides still refuse `whole`. Also add: pruning drops an id whose side the current form no longer derives (finding 5).

## F2 (High): "select only" is enforced for Delete and Ctrl+D only
Spine (AD-26): "With a right-side id in the selection, Delete and Ctrl+D are unavailable: the right half is select-only (EXPERIENCE.md)". EXPERIENCE Direct edits: "Right half, any workspace: select only"; Both halves: "its geometry fields are read-only".
Gap: the same paragraph lists "later nudge, rotate, P" as selection operations, and a drag, a nudge burst and the Inspector's multi-select typing ("multi-select typing is one command with many ids", l.230) all resolve the selection to authored nodes through `nodeIdOf`. A drag does not go through a builder at all: it passes its own input (a drop's delta, AD-26 invoke path), so the Delete-style check never sees it. Two stories (15.x drag, 14.x Inspector) obey every sentence and each lets a right-half key move the authored node, moving both halves, which is the very reason the amendment gives for refusing Delete.
Fix: state the rule once, at the selection level: "a right-side id in the selection makes every operation that edits authored nodes (Delete, Duplicate, nudge, rotate, drag, P, Inspector geometry fields) unavailable or read-only; operations that edit per-side data (overrides, keymap, netlist) address the SideId itself". Name who enforces it for gesture-passed input (the pointer layer must not start a drag on a right-side item), since a builder check cannot.

## F3 (Medium): nobody owns composing, parsing or re-qualifying a SideId
Spine: "a node's kind and parent are read from the design through `nodeIdOf(id)` (`model/main`), its side from the id"; hover "Hover holds a `SideId` the same way, so pointing at or selecting one side shows only that side's group border".
Gaps: `nodeIdOf` appears only in these two sentences. It has no return type (the bare `Id`, or the node?), is not in the glossary or Data Schema, and its inverse (build `<side>/<id>`), `sideOf`, and "the same side's parent group" do not exist. Hovering `right/key` must light `right/<parent of key>`; the Layout canvas (13.32 borders), the selection service (group click selects the innermost group), F (fit the group) and the add flow (parent rule) each need that and will each write their own string slicing, with unibody handled in some and not others.
Fix: one entry in the Data Schema (or an `Ids` helper beside `compareId`): `splitSideId`, `joinSideId(side, id)`, `nodeIdOf`, and a `sideParentOf(design, sideId)`; assign the package (the spine says `model/main`, but `schema` owns ids and `compareId`; decide, with the AD-10 import in mind).

## F4 (Medium): a selection can hold both halves of one node, and Delete/Duplicate build `ids` from it
Spine: "`SideId[]`, in selection order: `left/x`, `right/x`" and "shows row x selected when either side of x is".
Cases the sentences permit: box-select across the mirror axis ("Shift+drag always box-selects", EXPERIENCE) gives `left/x` and `right/x`; a Shift-click in the Tree on a row already selected via `right/x` adds `left/x`. Then (a) Duplicate/Delete's builder maps through `nodeIdOf` and passes `[x, x]` to a command whose schema may or may not accept duplicates; (b) a Tree click on a row "selected" only because of `right/x` is a toggle-off in one unit and a replace in another; (c) with `right/x` in the set, Delete is unavailable although the user sees a left key selected and the Tree row selected: a silent dead key (the spine gives no reason text, and "an unavailable Delete ... carries no reason", memlog, contradicts the earlier memlog line that the reason points at the Fitted toggle).
Fix: say whether a mixed set is allowed; if yes, builders dedupe after `nodeIdOf` and the Tree's toggle acts on the exact `left/x`; if no, selecting one side of a node removes the other. Give the dead key a visible hint (status strip or tooltip) instead of silence; it need not be a `Rejection`.

## F5 (Medium): hover has no stated owner or pruning; new-node selection can precede its posted row
Spine: pruning "After each commit it drops every id whose node the design no longer holds, from the design store's commit event" is stated for the selection service; hover "the same way" is a sentence fragment. Add flow: `finished` selects `right/<new id>`.
Gaps: (a) is hover in the selection service or its own service (13.32)? Two owners means two prunes or none; a hovered element that is removed by a command never fires `mouseleave`, so a stale hover shows a border for a deleted group until the pointer moves. (b) The new node's right-half row exists only when the model worker posts it (async, after the commit); selection holds `right/<new>` before any row exists, so F and the dim state read a missing row. Pruning by design membership passes it, the posted lookup misses it. (c) Pruning on form change, replaceDesign and undo is covered by the commit event, but a side the design stops deriving is not.
Fix: one `di` service for both (or say hover prunes with the same handler); say readers of a SideId with no posted row render nothing and fall back, not throw; say what F does with a selected id whose row is not yet posted.

## F6 (Medium): pick flows, the canvas-items registry and the stale ticket text
Spine: "`candidates(design, draft)` (the nodes it lights, and those it dims with a reason) and `choose(draft, target)`", "one `editor` function takes a press on a node from the canvas and the Tree, a pick when the top flow has `choose` and a selection otherwise; each canvas item reads its candidate or dimmed state from one computed".
Gap: `candidates` takes the design, which holds only bare ids, while canvas items are now keyed by `SideId`. A press on `right/x` as an anchor target either passes a `SideId` to `choose` (the anchor wants an `Id`) or is converted by the press function (but unibody `whole/x`, F1). One unit keys the candidate set by `Id` (both halves light together, contradicting the amendment's per-side highlighting), another by `SideId` (the design-level `candidates` cannot produce it).
Fix: say pick targets are bare `Id`; the press function applies `nodeIdOf`; candidate state lights the pressed side only or both, decided once.
Stale text to reconcile (not spine-internal): ticket 13.8 notes still say "Right-half group borders follow 13.32's rule (it draws every posted row's border)" and carry the open mirror-border question; EXPERIENCE.md Open Items still lists the `[GAP]` "whether selecting or pointing at a group on one side also shows its mirror's border", which the amendment now settles. 13.8's verify (select right/thumbfan-near-home selects it in the tree; pointing shows the right group's border; F fits one key) is consistent with the amendment. EXPERIENCE "Tree and canvas selection stay synced" holds only canvas-to-Tree for the right half: the Tree cannot select a right item, which is intended but worth one sentence in EXPERIENCE.
