Blueprint Walkthrough

Two changes on Corney Island, followed from what you do in the editor down to the code and data that run. The model shown is the one under discussion (operations build nodes; measuring forces one; the stage evaluates the returned tree). Numbers use Corney's choc v2 values: 19 mm key spacing, 18 × 18 mm keycaps, so gap x = 1 mm. API names are invented for the example.

Story 1

You make the home thumb key 1.5u

1. Before anything happens: what's already there

In the editor

The Parts tab lists one design part, key. It applies the library blueprint choc-key, version 3, with LED on. Every slot uses it unless it says otherwise.

Underneath: the design file (AD-8, KDL) 
library-versions {
  blueprint "lib:blueprint/choc-key" version=3
}
parts {
  part "key" blueprint="lib:blueprint/choc-key" {
    inputs pitch="19mm" cap="18mm" led=#true size="1u"
  }
}
meta { defaultPart "key" gap-x="1mm" gap-y="1mm" }
Underneath: choc-key@3, the blueprint's source (shipped with the library) 
export const inputs = {
  size:  option(['1u', '1.25u', '1.5u', '2u'], { perSlot: true }),
  pitch: quantity('mm'), cap: quantity('mm'), led: boolean(),
}

export function parts({ size, pitch, cap, led }) {
  const w = units(size) * pitch - (pitch - cap)     // 1.5u → 1.5 × 19 − 1 = 27.5
  return {
    rectangle: rect(w, cap),                          // the keycap: what the chain steps by
    cutout:    { role: 'cutout', target: 'plate', purpose: 'switch', shape: rect(14, 14) },
    footprint: use('lib:blueprint/choc-footprint', { led }),
  }
}

2. You change the size

In the editor

You select the home thumb key. Slot inspector › This slot › size: you pick 1.5u.

Underneath: one command (AD-2) writes one override 
slot "thumb-home" { inputs size="1.5u" }

The design is replaced as a new frozen value. Nothing has run yet.

3. Only that slot's part re-runs

In the editor

Nothing visible yet; this happens inside the same frame.

Underneath: the parts computed for thumb-home

Its input slice changed (size 1u → 1.5u), so its computed is dirty. The other 49 slots' slices didn't change; their computeds keep their values and don't run.

crossing 1 of 1: host → sandbox 
parts({ size: "1.5u", pitch: 19, cap: 18, led: true })

Inside the sandbox, rect() and use() only build nodes. No geometry is computed there.

back: sandbox → host, a plain-data tree 
{ "rectangle": { "op": "rect", "w": 27.5, "h": 18 },
  "cutout":    { "role": "cutout", "target": "plate", "purpose": "switch",
                 "shape": { "op": "rect", "w": 14, "h": 14 } },
  "footprint": { "op": "pads", "pads": [ … 6 pads, LED pads included … ] } }

The host evaluates the tree with geometry's operations and stores the part: a 27.5 × 18 mm rectangle, a 14 × 14 mm switch cutout, the footprint.

4. The layout moves

In the editor

On the canvas the home thumb key widens, and the far thumb key slides outward along the fan.

Underneath: the chain step (spine, Data Schema)

step = (rectA + rectB) / 2 + gap x, along the chain's axis, carried through the 15° splay.

Story 2

You add underglow

1. You add it

In the editor

You add Underglow from the library to the build (where exactly is a UX question). Its inputs appear: inset 3 mm, spacing 25 mm, chain after keys.

Underneath: one build entry 
build {
  entry "glow" blueprint="lib:blueprint/underglow" {
    inputs inset="3mm" spacing="25mm"
  }
}
Underneath: underglow@1's source 
export const reads = ['outline']                     // declared read (AD-11)

export function extras({ inset, spacing }, { outline }) {
  const path = offset(outline, -inset)                // a node
  const n = Math.floor(length(path) / spacing)        // measuring forces `path`
  const leds = points(path, n).map((p, i) =>          // measuring again (path cached)
    part('lib:part/sk6812-mini', { at: p, chain: i }))
  return { parts: leds, firmware: { underglowCount: n } }
}

2. It runs, measuring as it goes

In the editor

LEDs appear along the inside of the outline, 25 mm apart.

crossing 1: host → sandbox 
extras({ inset: 3, spacing: 25 }, { outline: { region … 37 segments … } })
crossing 2: sandbox asks the host, synchronously 
length(path)   → host offsets the outline by −3 mm, keeps it → 412.6

n = floor(412.6 / 25) = 16, computed inside the sandbox.

crossing 3: sandbox asks again 
points(path, 16) → [ { x: 104.2, y: -96.1, angle: 0 }, … 16 points … ]
back: the returned tree 
{ "parts": [ { "op": "part", "ref": "lib:part/sk6812-mini",
               "at": { "x": 104.2, "y": -96.1, "angle": 0 }, "chain": 0 }, … ],
  "firmware": { "underglowCount": 16 } }

The extras stage places 16 LED parts (with pins, so they join the netlist, AD-14). The firmware stage later reads underglowCount.

3. You drag a key near the edge

In the editor

The outline follows the keys, so the LEDs re-flow along it while you drag.

The outline is underglow's declared read, so its slice changes on every frame of this drag and the lane re-runs each frame: 3 crossings per frame (about 50 µs), plus the host's offset and sampling work.

Open: the host's offset work isn't counted by the sandbox's step budget. The spine already notes a makerjs offset of Corney's outline takes about 70 ms, more than a frame (Open Questions, 2D offset latency).

Story 3

A blueprint goes wrong

In the editor

You upgrade choc-key to a version with a bug that loops forever for 1.5u. The two 1.5u slots show their previous keycaps, marked stale, and the status strip counts a lane-failed error naming key and the slots.

parts({ size: "1.5u", … })  → stopped at step budget after ~2 ms
→ violation { kind: "lane-failed", severity: "error",
              ids: ["key", "thumb-home", "thumb-home-r"], … }

The other 48 slots ran fine. The two failed ones keep their last good rectangle, so the layout doesn't jump (AD-11).

Open: on the next edit, are these two retried (2 ms each again) or skipped until the inputs or the version change?

What to take from it
  • A blueprint is a file of JS: it declares inputs and reads, and has one function per lane that takes values and returns a tree.
  • You never see the sandbox; you see inputs in the Inspector, outputs on the canvas, and violations in the status strip.
  • A key costs one call when its inputs change and nothing otherwise. Underglow costs three calls per run, and runs whenever the outline changes.
  • The real risk this surfaces isn't the sandbox; it's host geometry work inside live lanes (the offset).
