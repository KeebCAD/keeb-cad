Blueprint Interactions

How a blueprint is run in six cases, drawn for the model under discussion: operations build nodes inside the sandbox, a measuring call forces one node, and the returned tree is evaluated by the stage. Nothing here is decided.

Crossing = one call between the host and the sandbox (about 10–15 µs in the spike, more with large payloads).

Under the "calls" model every operation would be its own crossing; each case notes where that changes the picture.

Orange marks a question the architecture has to settle.

Case 1 · parts lane · live

A key blueprint runs when its inputs change

sequenceDiagram
  autonumber
  participant U as Command (size 1u → 1.5u)
  participant G as Reactive graph
  participant H as blueprint host
  participant S as Sandbox (key@3)
  participant O as geometry ops
  U->>G: design replaced (AD-2)
  G->>G: slot's input slice changed? cache by slice hash
  G->>H: run parts lane (key@3, inputs)
  H->>S: parts(inputs)  [crossing]
  S->>S: rect(), cutout(), footprint() build nodes
  S-->>H: tree as plain data
  H->>O: evaluate tree
  O-->>H: rectangle, cutout, pads
  H-->>G: part outputs, violations
  G->>G: chain step reads the rectangle (13.2)
  • One crossing per run. Under the calls model: about 4–6.
  • A key drag changes no part input, so steps 3–9 do not run at all; only a size change or a parameter scrub does.
Case 2 · extras lane · live

Underglow measures its own path

sequenceDiagram
  autonumber
  participant G as Reactive graph
  participant H as blueprint host
  participant S as Sandbox (underglow@1)
  participant O as geometry ops
  G->>H: run extras lane (inputs, outline)
  H->>S: extras(inputs, outline)  [crossing]
  S->>S: path = offset(outline, -inset) builds a node
  S->>H: length(path) forces the node  [crossing]
  H->>O: evaluate offset
  O-->>H: path (cached for this run)
  H-->>S: 182.4
  S->>H: points(path, n)  [crossing]
  H-->>S: n points (from the cached path)
  S->>S: place LED parts, chain order, ledCount
  S-->>H: tree
  H->>O: evaluate the rest (path reused)
  H-->>G: LED parts, firmware config
  • Three crossings. Only the measuring calls cost one each.
  • Open: host work isn't counted by the sandbox's step budget; does the host need its own budget (operations, vertices)?
Case 3 · case lane · background

The tray builds the case body in the worker

sequenceDiagram
  autonumber
  participant G as Reactive graph
  participant PL as pipeline
  participant C as case stage (worker)
  participant S as Sandbox (tray@2)
  participant R as replicad ops
  G->>PL: committed revision
  PL->>PL: input slice: outline, pulled cutouts and mounts, query tallest-part
  PL->>C: slice  [thread crossing]
  C->>S: case(inputs, reads)  [crossing]
  S->>S: offset, extrude, subtract build nodes
  S->>C: bounds(inner) to place bosses  [crossing, optional]
  C->>R: evaluate offset
  R-->>C: inner wall
  C-->>S: bounds
  S-->>C: tree with spots (host-resolved selectors)
  C->>R: evaluate solids
  R-->>C: bodies, STEP, STL
  C-->>PL: CaseOutput  [thread crossing]
  PL-->>G: shown, stale if the slice moved on
  • No frame budget here: measuring is cheap relative to OCCT.
  • Pulled cutouts and mounts are already evaluated upstream; the tray never reads the bodies it contributes to (AD-18).
Case 4 · nesting

A key uses a footprint blueprint

sequenceDiagram
  autonumber
  participant H as blueprint host
  participant S as Sandbox (key@3)
  participant N as choc-footprint@2 (same context)
  H->>H: resolve pins: key@3 needs choc-footprint ≥2 (MVS, AD-5)
  H->>S: load key@3 and choc-footprint@2 code
  H->>S: parts(inputs)  [crossing]
  S->>N: use('choc-footprint', { hotswap })
  N-->>S: nodes (no crossing)
  S-->>H: one tree with the nested nodes inside
  • Nested code runs in the same sandbox and lane (AD-18), so nesting adds no crossings.
  • Open: does the nested blueprint get its own frozen scope inside the context, so it can't see the caller's state?
Case 5 · failure

A runaway blueprint during a parameter scrub

sequenceDiagram
  autonumber
  participant G as Reactive graph
  participant H as blueprint host
  participant S as Sandbox (bad-key@1)
  G->>H: run parts lane, frame n
  H->>S: parts(inputs)  [crossing]
  S->>S: while (true) …
  S-->>H: interrupted at step budget (about 2 ms)
  H-->>G: lane-failed, last good output marked stale (AD-11)
  G->>H: frame n+1, input changed again
  Note over G,H: 50 slots × ~2 ms ≈ 100 ms per frame while it keeps failing
  • Open: when does the host stop calling a lane that keeps failing (same inputs, same blueprint version)?
  • Open: the step count can drift by one with call history (accepted in the spike); does that hold here?
Case 6 · data form

The design's own shape goes through the same operations

sequenceDiagram
  autonumber
  participant G as Reactive graph
  participant M as model's data interpreter
  participant O as geometry ops
  G->>M: shape "thumb-plate" (data, AD-17 expressions)
  M->>M: evaluate expressions with model's evaluator
  M->>M: build the same node tree a code blueprint returns
  M->>O: evaluate tree
  O-->>G: region
  • No sandbox: data can't loop, so it needs no step budget.
  • One node vocabulary and one evaluator for both forms is what "one op API serves both" would mean in this model.
