## Intent

**Problem:** Story 13 grades both engines on the same scorecard, but the custom router (story 8) has only routed 131 matrix connections of wired Corney in Node. It has no worker run, no time or memory in a browser, no wireless result and no scorecard (R2), and R7 needs the strictest-clearance policy shown on the custom side too.

**Approach:** Run `routeConnections` on every `key-cell` and `routing` connection (wired 333, wireless 152) in its own Vite Web Worker under headless Chromium, and score it with the same pipeline as tscircuit through a new `pnpm score:custom`, writing `scorecards/custom-{wired,wireless}.scorecard.json`.

## Boundaries & Constraints

**Always:**
- Same connection set, same `RoutingInput` rules, same cap (600 s), same network blocking, same heap sampling (CDP `Runtime.getHeapUsage`, every 100 ms), same `drc` and KiCad scoring (bare and routed board, `added`, `addedUncertain`, `crossCheck`, `unrouted`) as `score:tscircuit`. One shared scoring path, so the two scorecards are comparable field for field.
- The router stays pure and deterministic; the worker only calls it. The page builds `RoutingInput` from `CORNEY[design]`, so `workerMs` is routing time only.
- Every value the router uses still comes from `RoutingInput` (R7, C6). An unroutable connection stays in `unrouted` and in the scorecard (C6).
- `score:tscircuit` keeps its behaviour and output format; its scorecards are not regenerated by this story.
- Decision (2026-10-27): the router gets a bounded, deterministic rip-up-and-reroute pass. A probe gave wired 327/333 and wireless 152/152 with 0 added `drc`; each of the 6 unrouted wired connections routes alone, so routing order blocks them, not the rules. After the first pass, each unrouted connection is routed with the router's own earlier copper as a per-step cost (`crossCost`) rather than an obstacle, the connections its path crosses are ripped up, it is placed, and the ripped ones are rerouted, for a fixed number of rounds. Whatever is still unroutable stays in `unrouted`. The asymmetry (our engine tuned, tscircuit only adapted) is recorded in the README for story 13.
- Decision (2026-10-27, review pass 1): `crossCost` stays at 3 mm. Ignoring our own copper outright gave wired 329/333; the 3 mm default was picked by a sweep on wired Corney itself (0.3 → 331, 1 → 332, 3 → 333, 10 → 332). It is a search cost, not a clearance rule, but it is tuned on the graded board, and the README and story 13 say so.

**Never:**
- No `reroute` field and no `moveKey` use (story 10). No tier or grading (story 13).
- No loosening of any clearance or width, no dropping of connections, no per-board tuning of rules.
- No changes outside `spikes/`.

## Implementation Notes

- `scripts/score.ts` holds serving, blocking, `routeInBrowser` (generic over the worker's answer), `scoreRoutes(design, text, input, routes, notes, run, kicadVersion, engine)`, `writeScorecard` (summary line), `withBrowser`, `probe` and `runScript`. `score-tscircuit.ts` keeps the adapter, `?external` and the reroute; its card is built by the same code in the same field order.
- `src/main.ts` now makes each worker on first use (tscircuit or custom), so an idle tscircuit worker never appears in the custom run's heap samples. `new Worker(new URL(...))` stays written out at each call site (the form Vite bundles).
- Router: `RouteResult` gains `timedOut`; options `ripUpRounds` (3), `crossCost` (3 mm), `deadlineMs` + `now`. Fields are a static-only base per width, copied (raster `slice`) for the with-our-copper field, which is dropped whole on rip-up and rebuilt lazily.
- The no-kicad-cli and `--probe` tests now run for both scripts (`describe.each`).
- Results: wired 333/333 in 13.0 s, wireless 152/152 in 2.6 s (committed run; an earlier run gave 5.4 s and 1.1 s; story 8's test also takes 3.8 s at the story-8 commit now, against 1.6 s then, so the machine slowed, not the code), 0 added `drc`, 0 added KiCad. KiCad warns `hole_to_hole`/`holes_co_located` for stacked same-net vias (in `kicad.other`, recorded in the README).
