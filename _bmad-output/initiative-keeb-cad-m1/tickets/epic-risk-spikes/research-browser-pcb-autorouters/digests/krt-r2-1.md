11. Clearance is one global option. Margins are computed as `width/2 + options.clearance + extra_margin` for obstacle-to-wire and as via pad/2 + clearance for vias. Wire-to-wire clearance for traces routed earlier in the same run uses each trace's own width plus the global clearance. Vias are inserted automatically with a single via pad diameter. The board edge is the rectangular `bounds`, enforced by blocking everything outside it (`add_board_bounds`). There is no separate edge-clearance setting. | wasm.rs lines ~705-852 | tscircuit | 2026-08 | accessed 2026-10-26 | high | capability
12. Failure semantics: connections are routed one after another. If one path fails (`path.ok_or_else(...)?`), that whole ordering strategy fails. Four fixed orderings are tried (CenterOut/Original, AdjacentFirst/ShortestFirst, Physical/Reverse, ReversePhysical/LongestFirst). If all four fail, the call throws "KRT GridRouter exhausted route-plan retries". It never returns partial routes, and the WASM path has no rip-up-and-reroute (the README lists "Rip-up and reroute orchestration" as not implemented). | wasm.rs lines 267-306, 307-440; npm README | tscircuit | 2026-08 | accessed 2026-10-26 | high | capability

## Per-candidate gate and criterion notes

### @tscircuit/krt-wasm 0.1.9 (WASM fork)
- G1 no network: likely pass. The WASM is inlined as base64 and there is no fetch or fs (F6).
- G2 licence: pass. MIT, upstream copyright retained (F1, F3). No GPL derivation found in the Rust core (F2, medium confidence).
- G3 Web Worker: likely pass, untested. The `nodejs` target, sync `WebAssembly.Module` and `atob` fallback contain nothing Node-only (F5, F6). A run cannot be stopped mid-route except by `worker.terminate()` (F9).
- G4 existing copper as fixed obstacles: partial. There is no trace/segment input, so saved routes would have to be turned into axis-aligned rect obstacles on a layer (F10). Orthogonal segments fit directly. 45-degree segments would need many small rects or would block extra space. `connectedTo` would let the router reuse same-net copper (F10, wasm.rs exemption). Unverified: whether connecting to an existing same-net stub works when the endpoint lies inside a rect.
- Keep-outs (3): only as rect obstacles. There is no polygon keep-out. A nice!nano module zone works as one or more rects (F10).
- Net classes / edge clearance (3): weak. Width can be set per connection, but clearance is one global value. The edge is a rectangular bounds only, with no outline polygon and no edge-clearance setting; a workaround is to shrink `bounds` (F10, F11).
- 2-layer quality (3): unknown. Grid A* with vias and fixed-order sequential routing. There is no rip-up, and any single failure fails the whole call with no partial result (F12). That is a serious risk for incremental "route only the broken ones" use on a dense board.
- Browser speed (2): no numbers. A 0.1 mm grid with 300k max iterations per connection is the default (F9).
- Integration (2): small (about 265 KB of WASM), ESM, no runtime dependencies. But the types depend on the `tscircuit` peer, which pnpm strict / TS 6 would need shimmed (F7, F8). Rebuilding the fork with `--target web` looks feasible (only wasm-bindgen/serde with `--no-default-features`), but I have not tested it (F5).
- Ecosystem (2): the fork is small and quiet since 2026-08 and is cut from an old core (F14, F17).
- Determinism (1): probably deterministic, not verified (F13).

### drandyhaas/KiCadRoutingTools (upstream)
- G2: MIT (F1). G3 as shipped: fail. It is a PyO3 cdylib, so it needs a port or a feature split like the fork's (F4).
- It has the features the fork lacks: polygon/User-layer keep-outs, Edge.Cuts arcs, net classes, rip-up-and-reroute (F15). But they are implemented largely in Python orchestration, so they would not carry over to WASM without re-implementing them (inference from F10/F15 and the repo being mostly Python).
- Ecosystem: very active, but the churn is so high (about 5.6k commits in 6 months, AI-driven) that any vendored fork goes stale quickly (F16).
