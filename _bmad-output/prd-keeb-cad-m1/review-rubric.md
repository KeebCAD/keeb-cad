# PRD Quality Review — keeb-cad milestone 1

Calibration: personal/hobby stakes, one builder who is also the only user, lean PRD on purpose. Editor views and gestures are left to a UX session by decision. Decisions in `.memlog.md` are treated as settled. The PRD feeds UX, an architecture update and stories, so done-ness and downstream use get the most weight.

## Overall verdict
This is a strong lean PRD. The thesis is clear (the layout is the single source of truth, so a change costs nothing downstream). The §4.0 control/follow matrix closes the gap the brief left open. Success metrics use real tolerances against a real reference board, and counter-metrics are named. The main risk is the milestone's dependence on browser routing. FR-12 calls the KiCad escape hatch "the milestone-1 fallback", SM-3 says that fallback is "not a pass", and nothing says what happens to M1 if the routing spike fails. Smaller done-ness gaps: which stages are "live", what makes a saved route "still valid", the mirrored side mode, and what SM-2 compares. All are cheap to fix, and none goes to the core of the document.

## Decision-readiness — adequate
Decisions are stated as decisions: tray only (FR-14), modules only with no bare chips (FR-12, glossary "Module"), ZMK only with a firmware-neutral model (FR-15), no manual trace editing (FR-12 `[NON-GOAL]`), and an authored outline that reverses the paper test (FR-7 Notes). The PRD names what each choice gives up: "the tool never pretends routing is solved" (§1), case solids rebuild "in the background with visible progress" (FR-14) instead of the brief's live case, and "Sameness across different users' designs is not a goal" (§7). The Open Questions are real open questions, not rhetorical ones.

The gap is that the riskiest open question has no decision attached. OQ1 ("can any engine route incrementally in the browser?") is what M1 depends on. FR-12 says "If routing cannot be solved in the browser, the KiCad escape hatch is the milestone-1 fallback". SM-3 says "this is a fallback, not a pass". §6 says "Done means the files pass fab checks". Read together, a failed spike means M1 cannot finish, yet the fallback is presented as planned. The same problem appears on a smaller scale with OQ2 (ZMK wired split): if the pinned ZMK version cannot do TRRS split, SM-4 fails for the wired variant and no fallback is named.

### Findings
- **high** Routing-spike failure leaves M1's definition of done unresolved (§4.5 FR-12, §8 SM-3, §6, §9 OQ1). FR-12 treats "the KiCad escape hatch is the milestone-1 fallback" as planned, while SM-3 says "this is a fallback, not a pass". The PRD does not say whether a failed spike blocks M1, changes its scope, or turns into an M1 that passes with KiCad plus external Freerouting. *Fix:* add a decision rule to OQ1: spike first, then name the outcome. One option is "if the spike fails, M1 is re-scoped to KiCad export + external routing and SM-3 is re-baselined". Another is "M1 stays blocked until routing works". Make FR-12 and SM-3 use the same wording.
- **medium** ZMK wired split has no fallback (§9 OQ2, SM-4, FR-15). SM-4 requires "ZMK firmware for both variants builds", and OQ2 asks whether the pinned version supports TRRS split at all. *Fix:* say what happens if it does not (newer ZMK version, wired variant firmware deferred, or a QMK exception) so that SM-4 cannot fail without a plan.
- **low** No sequencing inside a large milestone (§6 "FR-1 to FR-18"). All 18 FRs carry equal weight, and the scope covers the whole pipeline, including a browser autorouter, for one hobby builder. 📐 Because nothing is marked as checked first, it is easy to sink months into the editor before the routing risk is retired. *Fix:* one line in §6 ordering the work, for example "routing spike → layout/outline (SM-1) → PCB/routing → case → firmware". Alternatively, mark the routing spike as the gate before any other work.

## Substance over theater — strong
No theater found. There is one protagonist (Sergii), and §2.2 Non-Users does real work: "Other builders. Demand from others is unproven". The Vision (§1) is specific to this product ("move a thumb cluster, swap MX for Choc, go wireless … Ergogen config, KiCad, a CAD case and firmware") and could not be dropped into another CAD PRD unchanged. The NFRs in §7 are product-specific. "Stable outputs" spells out what is saved, what is cached and what is recomputed. "Live latency: no target yet" is an honest gap rather than a made-up number. Differentiation is limited to the positioning lines and is not padded out.

## Strategic coherence — strong
The thesis is explicit: the layout is the single source of truth, and edits propagate everywhere with no manual realignment (§1). The FRs follow from it. Each output section has a "follows a layout change" consequence (FR-1, FR-7, FR-9, FR-10, FR-11, FR-12, FR-14, FR-15, FR-16), and the §4.0 matrix ties them together. The MVP is a coherent kind: a problem-solving proof, end to end on one board. SM-1 to SM-4 check how faithfully the board is rebuilt. SM-5 checks the thesis directly. SM-C1 ("Passing SM-1 by hard-coding Corney shapes defeats the point") and SM-C2 are well-aimed counter-metrics.

### Findings
- **medium** The thesis is checked with only one edit (§8 SM-5). The core claim is "change it freely" (§2.1 JTBD 1), but SM-5 tests only "Moving one thumb-fan key". 📐 Four of the five primary metrics measure how faithful the rebuild is. Fidelity is necessary, but it is not the bet. Other edit types the vision names, such as a pitch or key-cell change (FR-3) or a part moved in one variant (FR-5), could break propagation and SM-5 would still pass. *Fix:* extend SM-5 to a short edit script, for example move a thumb key, shift a column, change the key cell, and move the reset switch in one variant, each with "zero manual edits" and "no unmarked stale output".

## Done-ness clarity — adequate
Most FRs have a testable consequence, and several are unusually sharp: FR-2's frame rule "must reproduce Ergogen's placement within ±0.05 mm", FR-13's "DRC that passes with zero errors" and "opens in KiCad 10 without errors", FR-17's "No output ever shows stale results without marking them stale", and FR-7's "moves exactly the vertices anchored to that column's nodes". The weak spots are listed below. Not having a latency number is a recorded decision and is not counted against the PRD. The problem is that "live" and "background" are not assigned to stages in one place.

### Findings
- **medium** Live vs background stages are never listed in one place (FR-17 "live stages update immediately, background stages show progress"; glossary "Live"; §4.0). Routing and case are background (FR-12, FR-14), plates are live (FR-10), and key-cell tracks are live (FR-12). Outline, nets/matrix and firmware are never assigned. "Stage" is also not a glossary term. *Fix:* add a "Live / Background" column to the §4.0 matrix and define "Stage" in §3.
- **medium** "Still valid" route is undefined (FR-12 "routes that are still valid are kept and only broken connections are rerouted"; §4.0 PCB row). An engineer cannot test incremental rerouting without a validity rule. *Fix:* define it, for example "a saved route is valid if its net still exists, its endpoints match the moved pads, and it passes DRC against the new geometry. All other routes are broken."
- **medium** Mirrored side mode has no acceptance condition (FR-4, glossary "Side mode", §9 OQ7). FR-4's only consequence covers reversible. Mirrored is defined as "two geometries with overrides", and OQ7 admits it is "untested on a real board". Corney Island is reversible, so nothing in M1 exercises mirrored. *Fix:* either add a consequence, for example "Heatwave's halves are expressible as mirrored with per-side overrides; paper check", or mark mirrored as model-ready only, the same way unibody is.
- **medium** SM-2 does not list what it compares (§8 SM-2 "matches Corney Island's case dimensions within ±0.05 mm"). The numbers exist in `addendum.md` (wall 1.2, tolerance 0.25, floor 1.0, height ~6.6, M2 screw radii, 8×40 cutout), but the metric does not reference them. "~6.6 mm" cannot be checked to ±0.05. *Fix:* name the compared dimensions and point to the addendum list. Turn "~6.6" into a value derived from the stack.
- **medium** Footprint differences are not reflected in SM-1/SM-3 (§8; memlog 2026-10-25 "SM-1/SM-3 comparisons account for footprint differences"; FR-8 "keeb-cad's own library"). SM-1 compares plate cutouts to ±0.05 mm, but a footprint library derived from ceoloide's may legitimately differ from Corney's. The decision was logged but did not reach the PRD. *Fix:* add a clause to SM-1/SM-3 saying which differences are excused (for example "cutouts and pads compared after substituting the reference footprint" or "only key centres and outline vertices are compared strictly").
- **medium** Keymap editor scope is undefined (FR-16 "author the keymap (keys and layers)"). It is not clear whether hold-taps, combos and behaviours are in scope, or what happens to a keymap entry when its key is deleted or a key is added. SM-4 ("firmware builds") does not check the keymap's content. *Fix:* name the supported keymap features for M1 (for example keycodes and layer switches only) and add "deleting a key removes or flags its keymap entries".
- **low** "The fab's checks" names no fab (FR-13, SM-3, §6). *Fix:* name the target (for example JLCPCB's online gerber viewer/DFM) so that "pass" is reproducible.
- **low** FR-18 autosave has no recovery behaviour ("The design autosaves in the browser"). *Fix:* add a consequence, for example "reopening the tab after a crash restores the last autosave".

## Scope honesty — strong
§5 Non-Goals does real work. It closes doors a reader might otherwise assume are open: Ergogen config import, KLE, KiCad import, user-imported parts and QMK. Inline `[NON-GOAL]` markers sit exactly where an omission could be assumed (FR-4 unibody, FR-12 manual traces). The narrowing of the brief's "case updates live" is visible in FR-14 and §4.0. Open-items density is low (7 OQs, 0 open assumptions, no `[NOTE FOR PM]`), which suits hobby stakes where the PM is also the decision-maker. The demand risk is stated honestly (OQ5, "no interviews").

### Findings
- **low** Unconfirmed items appear inline without a tag (FR-8 "likely derived from ceoloide's footprints with attribution (licence to verify)"). They are covered by OQ6, but §0 promises that inferred items carry `[ASSUMPTION]`, and §10 says "None open". *Fix:* point FR-8 to OQ6 explicitly, or soften §10 to "none open; open items tracked in §9".

## Downstream usability — strong
The glossary is thorough and mostly used consistently. FR, SM and SM-C IDs are contiguous and unique. Every SM names the FRs it validates. The addendum's "Architecture impact" list tells the architecture update exactly where the PRD departs from the spine, which matters for the next step. The §4.0 matrix can be pulled out alone and gives UX and architecture one place to read user control and follow behaviour per output. There are no UJs, which is appropriate (see Shape fit).

### Findings
- **low** FR-18 is the only FR that no SM validates (§8). Undo, migrations and stable ids have no success check. That is fine for hobby stakes, but story authors will find no SM to cite. *Fix:* optional. Add "undo/redo restores identical outputs" to SM-5 or §7 Stable outputs.

## Shape fit — strong
This is a single-operator hobby tool shaped as a capability spec, with a control/follow matrix instead of user journeys, which is the right shape. The weight goes where the memlog says it should ("lean PRD, heavy only on per-output control matrix"). Leaving editor views and gestures out ("views, panels and the meaning of dragging a key are decided in a separate UX session", FR-18 Notes) is stated, not hidden. It is not over-formalized: there are no personas, no UJ ceremony and no compliance padding.

## Mechanical notes
- **Undefined or drifting terms:** "stage", "live stages" and "background stages" (FR-17, §4.0, §7) are not in the glossary. "Peripherals" (glossary Routing, FR-12) is not defined; "Part" probably covers it. "Board origin" (FR-7) is not defined. "check 1" (§8 heading "Primary (check 1)") is brief-era vocabulary that the PRD never defines, so drop it or define it.
- **Possible confusion:** "key outline" (a geometry operation in glossary Shape, FR-6) and "Outline" (the board edge) look alike. Consider "key footprint shape" or "key-outline operation".
- **IDs:** FR-1 to FR-18, SM-1 to SM-5 and SM-C1 to SM-C2 are contiguous with no duplicates. The SM→FR cross-references resolve. §0 → §4.0 and §10 resolve.
- **Assumptions Index roundtrip:** there are no inline `[ASSUMPTION]` tags and §10 says "None open", so the roundtrip is consistent. The memlog assumption about ZMK split support appears as OQ2, correctly.
- **Required sections:** all present for the stakes (Vision, Target User, Glossary, Features, Non-Goals, Scope, NFRs, SMs, OQs, Assumptions).
